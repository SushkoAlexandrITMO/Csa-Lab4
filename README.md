## Язык программирования

Lisp-диалект с обязательной поддержкой рекурсивных функций.

### Синтаксис (Бэкус-Наур)

```
<program>     ::= <form>*
<form>        ::= <atom> | <list>
<atom>        ::= <integer> | <string> | <symbol>
<list>        ::= "(" <form>* ")"
<integer>     ::= ["+"|"-"] <digit>+
<string>      ::= '"' <char>* '"'             ; экранирование \n \t \" \\
<symbol>      ::= <symchar>+                   ; любые непробельные, кроме ()";

<special>     ::= "defun" | "setq" | "if" | "progn" | "let"
                | "+" | "-" | "*" | "/" | "mod" | "neg" | "1+" | "1-"
                | "=" | "<" | ">"
                | "print-int" | "print-char" | "read-char" | "halt"
                | "print-string" | "read-string"
                | "load" | "store" | "store-at" | "buffer-of"

<defun>       ::= "(" "defun" <symbol> "(" <symbol>* ")" <form>+ ")"
<setq>        ::= "(" "setq" <symbol> <form> ")"
<if>          ::= "(" "if" <form> <form> [<form>] ")"
<let>         ::= "(" "let" "(" <binding>+ ")" <form>+ ")"
<binding>     ::= "(" <symbol> <form> ")"
<call>        ::= "(" <symbol> <form>* ")"
```

Комментарий `; ...` — до конца строки.

### Семантика

- **Стратегия вычислений** — applicative order: аргументы вычисляются слева направо до вызова.
- **Любая форма — выражение.** `setq`, `if`, `let`, `progn` оставляют значение на стеке. Это позволяет `(print (setq x 13))`, `(setq y (if c 1 2))`, и так далее.
- **Области видимости** — две: глобальная (объявляется `setq` на верхнем уровне или внутри функций — но всегда на глобальный слот) и лексические локалы (`let` и параметры `defun`). Имя, ссылающееся на лок при компиляции, всегда находится в стек-каркасе функции; в глобал смотрим только если ни один локальный слот не подошёл.
- **Типизация** — динамическая, но фактически используется один тип: 32-битное знаковое целое. Литералы: `42`, `-17`, `"строка"` (адрес pstr в data-сегменте), символы (имена переменных/функций).
- **Рекурсия** — поддержана через стек возвратов (`CALL`/`RET`). Хвостовая оптимизация не применяется: каждый рекурсивный вызов добавляет кадр.

### Отображение выражений на регистры/память

Стековая архитектура: все промежуточные значения живут на data-стеке.

- **Литералы (`int`)**: если значение помещается в знаковый 16-битный operand — `PUSH imm`; иначе слово выделяется в data-сегменте и грузится через `LOAD addr`.
- **Литералы (`string`)**: интернируются в data-сегмент как pstr (длина в первом слове, затем символы по одному на слово); выражение оставляет адрес pstr на стеке.
- **Переменные**:
  - локальные/параметры → компилятор отслеживает «стек-каркас» и эмитит `DUP` (глубина 0), `OVER` (глубина 1) или `PICK n` (глубина ≥ 2);
  - глобальные → `LOAD addr` из data-сегмента.
- **Инструкции, процедуры, прерывания**:
  - инструкции хранятся в code-сегменте, начиная с `0x1000`;
  - процедуры — обычные блоки с меткой; точка входа — `CALL <label>`;
  - прерывания в нашем варианте (stream) отсутствуют — в `memory[1..0xF]` зарезервирован вектор, но не используется.

## Организация памяти

### Регистры, видимые программисту

| Имя | Размер | Назначение |
|---|---|---|
| TOS | 32 бита | Вершина data-стека (видна как «верхний элемент» при выполнении опкодов) |
| DS | стек | Data-стек (TOS — его вершина; нижние элементы в DS) |
| RS | стек | Return-стек (адреса возврата CALL/RET) |
| A | 16 бит | Адресный регистр; используется только опкодами `LDA / LDAI / STAI` |
| B | 16 бит | Адресный регистр; используется только опкодами `LDB / LDBI / STBI` |
| PC | 16 бит | Счётчик команд |
| AR | 16 бит | Адрес для обращения к памяти |
| DR | 32 бита | Данные из памяти / в память |
| IR | 32 бита | Текущая инструкция |
| Z, N | 1 бит | Флаги: Z = (результат == 0), N = (результат < 0) |
| mPC | 6 бит | Счётчик микроинструкций (внутренний для ControlUnit) |

A/B — **только адресные**, в ALU не участвуют. Это сохраняет stack-контракт варианта: арифметика — на DS/TOS.

### Карта памяти (фон-Неймановская, одно адресное пространство 65 536 слов × 32 бита)

```
+----------+-----------------------------+
| 0x0000   | JMP _start  (reset vector)  |
| 0x0001   |                             |
|   ...    |  резерв под векторы          |
| 0x000F   |                             |
+----------+-----------------------------+
| 0x0010   | литералы и pstr             |
|   ...    | глобальные переменные        |
|   ...    | буферы (buffer-of)           |
+----------+-----------------------------+
| 0x1000   | прелюдия (defun __pstr_*)   |
|   ...    | пользовательские defun       |
| _start:  | точка входа пользовательского|
|   ...    | кода                         |
| HALT     |                             |
+----------+-----------------------------+
```

- Слово 0 — JMP, который синтезирует линкер (это «reset vector»). PC сбрасывается в 0 при запуске.
- Data-сегмент (`0x0010..`): литералы, статические pstr-строки, глобалы (`setq`), буферы (`buffer-of`).
- Code-сегмент (`0x1000..`): прелюдия (`__pstr_print`, `__pstr_read` и их хелперы), затем `defun` пользователя, затем код верхнего уровня, начиная с метки `_start`, и `HALT` в самом конце.

### Что попадает куда

| Что | Хранится | Когда |
|---|---|---|
| Малый int литерал (`-32768..32767`) | в операнде команды `PUSH` | при компиляции каждого использования |
| Большой int литерал | отдельное слово в data-сегменте | один слот на каждый литерал |
| Строковый литерал | pstr в data-сегменте (длина + chars) | один слот на каждый литерал, адрес используется как значение |
| Глобальная переменная | одно слово в data-сегменте | один слот на имя; `setq` пишет, `load` читает |
| Локальная переменная (`let`, параметр `defun`) | data-стек | пока в области видимости; стек-каркас восстанавливается NIP-ом (`SWAP DROP`) при выходе |
| Буфер | подряд N слов в data-сегменте | возвращается `(buffer-of N)`; место под буфер ленивое — на каждом вызове новый |
| Инструкция | code-сегмент | заполняется линкером; место — единственное место расположения |
| Процедура | code-сегмент | начинается меткой `fn_<name>`, кадр RS строится `CALL`-ом |

## Система команд (ISA)

**Классификация:** Stack, RISC-подобная (фиксированная длина команды, единственный явный операнд). Архитектура — фон-Неймановская (общая память кода и данных), однопортовая.

### Формат команды

```
 31                    24 23                  16 15                            0
+------------------------+----------------------+------------------------------+
|     opcode (8 бит)     |   reserved (8 бит)   |       operand (16 бит)       |
+------------------------+----------------------+------------------------------+
```

- Опкод занимает старший байт, единственный операнд — младшие 16 бит (знак-расширяемые при PUSH, без знака при адресных операциях).
- Все команды одной длины (32 бита) — нет переменного числа слов на команду.
- Бинарный файл — сырой little-endian dump образа памяти, начиная с адреса 0.

`T` = такты на полный цикл (включая `FETCH`+`DECODE` = 2 такта).

### Кодирование

Бинарный файл сохраняется в формате сырых 32-битных слов little-endian, начиная с адреса 0. Отладочный листинг (`.lst`) имеет формат:

```
<addr>  <HEXCODE>  <mnemonic>           <label>: <comment>
```

Пример из `hello.lst`:
```
0000  02001067  JMP   0x1067      ; reset vector
0010  0000000D  DATA  13
0011  00000048  DATA  72
...
1067  06001023  CALL 0x1023       _start: CALL fn___pstr_print
```

## Транслятор

CLI: `translator <source.lisp> <output.bin> [--listing <output.lst>]`

Этапы:

1. **Tokenize** — посимвольный сканер S-exp: скобки, целые, строки (с escape), символы. Комментарии (`;`) отбрасываются.
2. **Parse** — рекурсивный спуск, AST — обычные Python-списки с атомами `int`, `Symbol`, `StringLit`.
3. **Prelude injection** — перед AST пользовательской программы вставляются процедуры прелюдии (`__pstr_print`, `__pstr_print_loop`, `__pstr_read`, `__pstr_read_loop`), написанные на нашем lisp.
4. **Collect top-level** — первый проход: регистрирует все глобальные имена и функции, чтобы позволить forward-ссылки.
5. **Compile** — обход AST с трекером стек-каркаса. На каждое выражение генерируется код, оставляющий значение на TOS.
6. **Link** — каждому `CodeItem` присваивается абсолютный адрес. Символические метки заменяются на адреса. Линкер также синтезирует `JMP _start` в `image[0]`.
7. **Emit** — образ памяти упаковывается в little-endian; параллельно генерируется человекочитаемый листинг.

### Компиляция «сложных» форм

| Конструкция | Шаблон кода |
|---|---|
| `(setq x v)` | code(v); DUP; STORE addr_of_x |
| `(if c t e)` | code(c); PUSH 0; CMP; JZ else; code(t); JMP end; else: code(e); end: |
| `(if c t)` без else | то же, но else-ветка эмитит `PUSH 0` |
| `(let ((x e1)) body)` | code(e1) ; (слот помечен как 'x'); body; SWAP; DROP |
| `(progn a b c)` | code(a); DROP; code(b); DROP; code(c) |
| `(+ a b)` | code(a); code(b); ADD |
| `(< a b)` | code(a); code(b); CMP; JS true; PUSH 0; JMP end; true: PUSH 1; end: |
| вызов `(f a b)` | code(a); code(b); CALL fn_f |
| `(defun f (a b) ...)` | JMP defun_end; fn_f: body; SWAP DROP; SWAP DROP; RET; defun_end: |

## Модель процессора

CLI: `machine <binary.bin> <stdin.txt> [--log out.log] [--tick-limit N]`

### Схема DataPath (ASCII)

```
                         +---------+
                         |   ALU   |
                         +----+----+
                              | result
                              v
   IR.operand  --[mux]----+---+----+--- DR <----+
   PC+1        --[mux]    |        |            |
   RS top      --+--[mux]-+        |     +------+
                           |       |     |
                           v       v     |
                       +---+----+  |     |   +-----+
                       |  PC    |  |     +-->|  AR |---> address bus
                       +--------+  |         +--+--+
                                   |            |
   memory bus <---------------+----+------------+
                              |
        +----+    +----+    +-+--+    +-+--+
        | A  |    | B  |    |TOS |    | DS |--- (stack of 32-bit words)
        +-+--+    +-+--+    +-+--+    +----+
          |         |          |
          +---+-----+----------+-----[mux]---> ALU inputs / DS push source
              |
              v
            data path

Flags: Z, N (latched from ALU result)
Stacks:
  DS — top-N elements below TOS, accessed by DS_PUSH/DS_POP/DS_REPLACE_TOP
  RS — return-stack, used by CALL/RET (RS_PUSH(PC), RS_POP)
```

Регистры TOS, A, B, PC, AR, DR, IR, флаги Z/N — все защёлки, обновляются по фронту такта.

DS и RS — стеки на регистрах общего назначения. В реальном железе это были бы небольшие SRAM с регистром-указателем; в модели они представлены как Python-списки, но обращение к ним идёт через те же сигналы (`DS_PUSH`, `DS_POP`, `DS_REPLACE_TOP`, `TOS_FROM_DS_AT_DEPTH`).

Мультиплексоры (помечены `[mux]`) выбирают источник для каждого latch'а: например, для `LATCH_PC` есть селекторы `PC_PLUS_ONE / PC_FROM_OPERAND / PC_FROM_RS_TOP / PC_FROM_OPERAND_IF_Z` и т. д. Селектор приходит от ControlUnit'а.

### Схема ControlUnit (микропрограммный, ASCII)

```
                  +---------+
   opcode  ------>|         |
   (из IR)        | DECODE  |---> address of executor
                  +---------+        |
                       ^             v
                +------+------+   +-------------+
                |    mPC      |<--|  next mPC   |<-- M_PC selector
                +------+------+   |   selector  |
                       |          +-------------+
                       v
              +--------------------+
              |   ROM микрокода    |
              | MicroInstr[0..46]  |
              +---------+----------+
                        |
                        v
           {signal, selector}*  — параллельные сигналы на DataPath за один такт
```

- `mPC` — указатель в ROM микрокода. На каждом такте читается одна `MicroInstr`, состоящая из набора одновременно активных сигналов.
- Точки входа: `mPC=0` — fetch (читает IR и инкрементирует PC), `mPC=1` — decode (выбирает handler через `DISPATCH(opcode)`), `mPC≥2` — handlers конкретных опкодов.
- Каждый handler заканчивается сигналом `LATCH_M_PC ← M_PC_FETCH`, возвращающим управление в fetch.

Сигнальные линии от ControlUnit к DataPath показаны выше пунктиром через мультиплексоры; в коде они описаны как пары `(Signal, Selector)`, поэтому на схеме каждый сигнал — это один селектор для одного мультиплексора.

### Точность модели

Симулятор тактируется по одному микро-такту в одном вызове `ControlUnit.tick()`. Соответственно, программу можно приостановить **на любом такте**, а не только на границе инструкции. Это используется и в тесте `test_tick_hook_can_stop_mid_instruction`, и в публичном `simulate(..., tick_hook=...)`-параметре.

Семантика такта — sample-before-write:
1. на начало такта снимается `Snapshot` всех источников;
2. комбинаторные пути (ALU, чтение памяти, peek порта) вычисляют выходы из снимка;
3. в конце такта одновременно защёлкиваются все приёмники (PC, AR, DR, IR, TOS, A, B, Z, N, mPC) и применяются стек-эффекты (DS_PUSH/POP, RS_PUSH/POP, MEM_WRITE, IO_WRITE).

## Микропрограмма

ROM микрокода — массив из 47 `MicroInstr`'ов (`csa_lab4/microcode.py`). Каждая запись — кортеж пар `(Signal, Sel)`, описывающих параллельно активные сигналы за один такт.

Карта ROM (адреса в скобках — стартовые точки handler'ов):

```
  0: FETCH     -- IR <- MEM[PC]; PC <- PC+1
  1: DECODE    -- mPC <- DISPATCH(IR.opcode)
  2: NOP       -- mPC <- FETCH
  3: HALT      -- halt
  4: JMP       -- PC <- IR.operand; mPC <- FETCH
  5: JZ
  6: JNZ
  7: JS
  8-9:  CALL.{1,2}  -- RS push PC, потом PC <- operand
 10:  RET           -- PC <- RS top; RS pop
 11-15: ADD/SUB/MUL/DIV/MOD
 16-17: CMP.{1,2}
 18-20: NEG/INC/DEC
 21-24: LOAD.{1,2}, STORE.{1,2}
 25-26: LOADI.{1,2}
 27-28: STOREI.{1,2}
 29: INPUT
 30: OUTPUT
 31: PUSH
 32-35: DUP/DROP/SWAP/OVER
 36-37: LDA / LDB
 38-39: LDAI.{1,2}
 40-41: LDBI.{1,2}
 42-43: STAI.{1,2}
 44-45: STBI.{1,2}

```

Полный пример микрокода для ADD:

```python
_mi(
    "ADD",
    (Signal.ALU_OP, Sel.ALU_ADD),       # выход ALU = NOS + TOS
    (Signal.LATCH_TOS, Sel.TOS_FROM_ALU),
    (Signal.DS_POP, None),               # один уровень снимается со стека
    (Signal.LATCH_FLAGS, None),
    (Signal.LATCH_M_PC, Sel.M_PC_FETCH),
)
```

Пять сигналов работают параллельно в одном такте: ALU считает сумму комбинаторно из снимка, TOS защёлкивается из выхода ALU, DS уменьшается на один, флаги обновляются, mPC возвращается в FETCH.

## Ввод-вывод

Вариант — **stream + port**: ввод-вывод посимвольный через специальные команды; адресация портов:

| Порт | Команда | Назначение |
|---|---|---|
| 0 | `INPUT 0` | прочитать ASCII-символ из входного потока. Если буфер пуст — `HaltError` (модель останавливается). |
| 1 | `OUTPUT 1` | вывести `chr(TOS & 0xFF)` в выходной поток |
| 2 | `OUTPUT 2` | вывести `str(TOS)` (десятичное представление числа) в выходной поток |

Логика буферов реализована на стороне симулятора Python (`csa_lab4/machine.py::IO`):

- При старте `input_buffer` инициализируется списком кодов символов из входного файла.
- `INPUT 0` снимает один элемент с головы; пустой буфер → исключение `HaltError("input buffer exhausted")`, которое симулятор перехватывает и завершает прогон корректно.
- `OUTPUT 1/2` дописывают строку в `output_chunks`, в конце симуляции конкатенируются и возвращаются как stdout программы.

Никаких прерываний нет (вариант `stream`, не `trap`); вектор прерываний в области `0x0001..0x000F` зарезервирован, но не используется.
